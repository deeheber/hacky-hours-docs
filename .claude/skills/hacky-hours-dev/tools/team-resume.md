# /hacky-hours team resume — synthetic resume per agent

Generates a markdown resume for an agent from the persistent context documents in the team repo. The resume is what an agent would hand to a new project: who they are, what they know, what they've actually done, what they've learned. Same shape as a human teammate's CV — composited from `profile.md`, `system-prompt.md`, `history.md`, `feedback.md`, and the derived-metrics frontmatter introduced in Slice 13.

The output is `agents/<agent-id>/resume.md` in the team repo. The team-site generator picks it up and links to it from the agent's profile page. Conductors can also `cat` it directly or paste it into a hiring-style context anywhere they need to introduce the agent.

Resumes are **fact-derived, not invented.** Every line traces back to a source in the team repo. No phantom skills, no inflated experience, no narrative embellishment beyond what the source documents actually support.

Contract source: `${CLAUDE_SKILL_DIR}/references/capture-format.md` §"Resume composition".

---

## Step 0 — Pre-flight

1. **Active team:** read project `AGENTS.md` for `team:` field; default to `default` if absent.
2. **Argument parsing:** `/hacky-hours team resume [flags]`
   - `<agent-id>` — positional; required unless `--all`
   - `--all` — generate resumes for every agent on the team
   - `--out <path>` — write to a custom path instead of `agents/<agent-id>/resume.md`
   - `--print` — print to stdout instead of writing; useful for piping
   - `--style minimal|standard|deep` — verbosity (default `standard`); see "Style presets" below
3. **Agent exists:** for non-`--all` invocations, verify `~/.hacky-hours/teams/<active>/agents/<agent-id>/` exists. If not: print *"Unknown agent `<agent-id>` on team `<active>`. Run `/hacky-hours team list` to see options."*
4. **Source files:** the verb reads (any may be absent — handle missing gracefully):
   - `agents/<id>/profile.md` — frontmatter (id, name, hats, tagline, joined, specialties, metrics) + Bio sections
   - `agents/<id>/system-prompt.md` — for the "Summary" section's voice anchor (do not include verbatim; condense)
   - `agents/<id>/history.md` — chronological contribution log (forward-captured + backfilled)
   - `agents/<id>/feedback.md` — durable behavior corrections
   - `agents/<id>/preferences.yml` — for declared focus areas (if present)

## Step 1 — Compose the resume

Generate `resume.md` with this structure (style: `standard`):

```markdown
---
agent: <agent-id>
generated: <ISO timestamp>
generator: team-resume v4.0.0
style: standard
source:
  profile_modified: <YYYY-MM-DD>
  history_entries: <count>
  feedback_entries: <count>
---

# <Name> <avatar> <Role>

> <tagline from profile.md>

**Level <N>**  ·  <history_entries> contributions  ·  <projects.count> projects  ·  joined <joined>

## Summary

<2-3 sentences distilled from the agent's system-prompt + profile bio. Should read like a 30-second introduction: who they are, what they're known for, how they engage. No fluff, no marketing language.>

## Skills

<Aggregated from history.md by verb-type + file-types-touched + project-variety. One line per skill area with the evidence count. E.g.:>

- **System design** — 18 ADRs authored, 12 ARCHITECTURE.md contributions across 4 projects
- **Codebase review** — 23 audit participations (Lane A roleplay)
- **Cross-role facilitation** — 7 arbitrate sessions as a named position-holder

Aim for 5-8 skill lines. Don't pad. If history is thin, skills list is short — that's honest.

## Experience

<Grouped by project, chronological newest-first within each project, oldest project last. For each project group, render the history entries with date + verb + summary.>

### <project-slug-1> · <first-date> → <most-recent-date>

- <YYYY-MM-DD> · <verb> · <summary>
- <YYYY-MM-DD> · <verb> · <summary>
- ...

### <project-slug-2> · <first-date> → <most-recent-date>

- ...

<For each project, the title line shows the active span. Backfilled entries are not annotated in the resume output — the (backfilled, ...) tag is internal-only.>

## Recent learnings

<From feedback.md — paraphrased durable corrections. One bullet per durable note. E.g.:>

- Lead with concrete file paths before schema discussion when reviewing framework-internal code (per conductor 2026-05-03)
- Calibrate threat-model framing to project tier — Tier 1 personal tools don't need a full STRIDE pass (per conductor 2026-04-21)

If feedback.md is empty or only has placeholder text: omit this section.

## Profile

<Verbatim include of profile.md's Background / How I work / What I produce sections. This is the hand-curated character anchor — preserve it.>

---

*Generated by `/hacky-hours team resume <agent-id>`. Sources: `agents/<id>/{profile,history,feedback}.md`. Re-run anytime to refresh.*
```

## Style presets

- **`minimal`** — Header + Summary + top 3 skills + 5 most recent experience entries (no per-project grouping) + Profile bio. Single-screen scan.
- **`standard`** *(default)* — Full structure above.
- **`deep`** — Standard + a `## System prompt excerpts` section showing 3-5 representative lines from `system-prompt.md` (the parts that describe behavior and defaults, not boilerplate). Useful when handing off the resume to a context that needs to understand *how* the agent thinks, not just *what* they've done.

## Step 2 — Compute fields

For the header line "Level N · M contributions · K projects":

- **Level** — read `metrics.level` from `profile.md` frontmatter. If absent, derive from `metrics.history_entries` per the formula in `references/capture-format.md` §"Level derivation". Default to 0 if no metrics block.
- **Contributions** — `metrics.history_entries` (count of lines in `history.md` matching the structured format).
- **Projects** — `len(metrics.projects)` (distinct project slugs the agent has appeared in).

For **Skills aggregation:**

Parse `history.md` and group entries by verb type. Map verb → skill area:

| Verb | Skill area |
|------|------------|
| `audit` | Codebase review |
| `adopt` | Project onboarding |
| `arbitrate:*` | Cross-role facilitation |
| `design` | Design documentation (per role's discipline) |
| `build:*` | Implementation (per role's discipline) |
| `ideate` | Product framing |
| `roadmap` | Roadmap shaping |
| `iterate` | Iteration synthesis |

Multiple verbs can roll up to a single skill area — combine counts. Cite the count + project breadth in the skill line.

For **Experience grouping:**

Parse `history.md`, group by project slug (third field of the structured format `<date> · <project> · <verb> · <summary>`). Within each project, sort entries newest-first. Sort projects by most-recent-entry date desc.

## Step 3 — Write the file

Write to `~/.hacky-hours/teams/<active>/agents/<agent-id>/resume.md` (or to `--out` path if provided).

**Don't commit automatically.** Resumes are derived artifacts — they change every time history changes. Auto-committing every resume regeneration would flood the team repo. Print a one-liner footer:

> *"Wrote resume.md (<N> lines, level <L>, <M> contributions, <K> projects). To commit: `cd ~/.hacky-hours/teams/<active>/ && git add agents/<id>/resume.md && git commit -m 'resume: <agent-id> regenerated <date>'`."*

If the conductor wants resumes tracked in git: they commit explicitly. If they want them ephemeral (regenerate on demand, never commit): just don't commit.

## Step 4 — `--all` mode

Loop Step 1–3 for every agent in `agents/` whose `profile.md` exists. Print per-agent status:

```
team resume --all (team: default)

  ✓ product/resume.md       (level 3, 14 contributions, 1 project)
  ✓ design/resume.md        (level 2, 5 contributions, 1 project)
  ✓ architect/resume.md     (level 4, 22 contributions, 1 project)
  ✓ frontend/resume.md      (level 0, 0 contributions) — minimal output (no history yet)
  ✓ backend/resume.md       (level 0, 0 contributions) — minimal output (no history yet)
  ✓ security/resume.md      (level 3, 11 contributions, 1 project)
  ✓ ops/resume.md           (level 2, 4 contributions, 1 project)
  ✓ qa/resume.md            (level 2, 5 contributions, 1 project)
  ✓ accessibility/resume.md (level 1, 3 contributions, 1 project)
  ✓ licensing/resume.md     (level 1, 2 contributions, 1 project)
  ✓ data/resume.md          (level 0, 0 contributions) — minimal output (no history yet)
  ✓ ai-ml/resume.md         (level 0, 0 contributions) — minimal output (no history yet)

12 resumes generated. Run /hacky-hours team site build to regenerate the static site (resumes will render with linked from profile pages).
```

Agents with zero history get a minimal resume (header + Summary + Profile only — no Skills/Experience/Learnings sections, since there's nothing to show). Honest about what they haven't done yet, rather than padding.

## Step 5 — Team-site integration

When the team-site generator runs and finds `agents/<id>/resume.md`, it:
- Generates a `<id>-resume.html` page in `docs/agents/`
- Links to it from the agent's profile page header
- Card grid on index page surfaces the level + contribution count

No changes needed by the conductor — `team site build` after `team resume --all` picks up the resumes automatically.

## Edge cases

- **Empty history.md.** Skills and Experience sections are omitted. Summary still works from profile + system-prompt. Resume is short and honest.
- **history.md exceeds the compaction threshold.** Read both `history.md` (recent) and any archived files in `history-archive/`. Aggregate metrics across both. The Experience section shows recent entries from `history.md`; archived entries roll up into skill counts but don't render line-by-line.
- **profile.md has been auto-rewritten (via Slice 13 reflection).** Resume picks up the latest version of the bio. No special handling — the source of truth is `profile.md`.
- **Custom or SME agent without standard role-doc ownership patterns.** Skill aggregation falls back to verb-only counts (e.g., "audit: 5 contributions" without a discipline label). Doesn't break, just less rich.

## Notes for the assistant running this

- **Honest over flattering.** A level-2 agent should not get a level-4-sounding summary. Match tone to actual seniority. Junior agents read as junior; senior agents read as senior. If the source data shows the agent has done thin work, the resume reflects that.
- **Fact-derived skill claims only.** Don't infer "expert at Postgres" from one history entry mentioning a DATA_MODEL.md edit. Count + project breadth is the evidence; skill claims have to be backed.
- **Resume is a snapshot, not history.** Regenerate freely. It's derived from sources, not the source itself.
- **Don't overwrite a hand-edited `resume.md`.** If `resume.md` exists and contains a frontmatter `generator:` field that's *not* `team-resume v4.0.0`, ask the conductor: *"This resume looks hand-edited. Overwrite, or write to a sibling path (`resume-generated.md`)?"*
